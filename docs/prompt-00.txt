dioxus-auth, Deep Investigation: User Creation & Developer Control

We already investigated the repository and established the basic facts.

Do not modify code. Do not implement anything. Do not propose a final API yet.

This investigation is much narrower than the previous one.

We are specifically trying to answer:

«How should dioxus-auth balance library-owned defaults with developer-owned user data and identity, so that beginners can start immediately without forcing advanced developers into the library's model?»

Ignore unrelated areas of the codebase unless they directly affect this question.

Do not spend time re-investigating session security, cookies, rate limiting, verification flows, Dioxus components, or unrelated authentication features. Only inspect them if they directly constrain user creation or persistence.

---

1. The problem we are investigating

The current API is roughly:

auth.sign_up_email(
    "alice@example.com",
    "password",
    AppUser {
        id: 1,
        email: String::from("alice@example.com"),
        name: String::from("alice"),
    },
)?;

This feels too low-level.

A developer who simply wants:

«"Create my first authenticated user"»

currently has to think about:

- what the user ID should be
- who generates it
- why the ID is needed
- why email is passed twice
- why the complete "User" must be constructed before signup
- which fields belong to authentication
- which fields belong to the application

We want to investigate whether the API can instead provide a default path where dioxus-auth handles the boring parts, while still allowing developers to take control when necessary.

---

2. Core philosophy

Do not interpret "developer control" as:

«"The developer must manually configure everything."»

That is exactly the problem we are questioning.

Instead investigate whether the architecture can provide:

DEFAULT
────────────────────────────
dioxus-auth handles common decisions
developer writes very little
identity can be generated automatically
common user creation just works


CONTROLLED
────────────────────────────
developer supplies custom User model
developer owns database
developer controls custom fields
developer can control identity strategy


FULL CONTROL
────────────────────────────
developer can replace/customize the underlying store
developer can use existing schema
developer can use existing IDs
developer can integrate external identity systems

The important question is whether these can be different levels of control over the same auth system.

We do NOT want:

BeginnerAuth
AdvancedAuth
CustomAuth

unless the codebase gives a compelling reason.

8. The duplicated email problem

Current API:

auth.sign_up_email(
    "alice@example.com",
    "password",
    AppUser {
        email: "alice@example.com",
        ...
    },
)?;

The investigation already found that these two values are not even checked against each other.

We need to understand the intended ownership.

Investigate these possibilities:

Option A

Email is only a signup/login identifier.

The User doesn't need "email()" at all.

Option B

Email belongs to the User, and signup derives the identifier from it.

Option C

The auth identifier is generic, and email is simply one possible user field.

Option D

Keep both because they represent different concepts.

For each, explain what the existing code implies.

Pay particular attention to the fact that ".email()" has no meaningful engine usage today.

Do not decide whether it should be removed yet.

11. Create vs attach

Investigate whether signup is currently conflating two operations:

Create a new application user

and:

Create authentication credentials for a user

The current method does both together.

Ask whether the architecture would be cleaner if these were conceptually separable.

For example:

create user
     +

versus:

     =

Do not automatically split them.
